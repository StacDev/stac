## Overview

The `conditional` widget renders different widgets based on a boolean expression evaluated at runtime. It evaluates the `condition` string against the current application state and renders either the `ifTrue` or `ifFalse` widget accordingly. This enables server-driven conditional UI logic without writing custom code.

## Properties

| Property    | Type         | Required | Description                                                                          |
|-------------|--------------|----------|--------------------------------------------------------------------------------------|
| `condition` | `String`     | Yes      | The boolean expression to evaluate at runtime against the current application state. |
| `ifTrue`    | `StacWidget` | Yes      | The widget to render when the condition evaluates to `true`.                         |
| `ifFalse`   | `StacWidget` | No       | The widget to render when the condition evaluates to `false`. Renders an empty `SizedBox` if omitted. |

---

## Basic Usage

<CodeGroup>
```dart Dart
StacConditional(
  condition: 'isLoggedIn == true',
  ifTrue: StacText(data: 'Welcome back!'),
  ifFalse: StacText(data: 'Please sign in'),
)
```

```json JSON
{
  "type": "conditional",
  "condition": "isLoggedIn == true",
  "ifTrue": {
    "type": "text",
    "data": "Welcome back!"
  },
  "ifFalse": {
    "type": "text",
    "data": "Please sign in"
  }
}
```
</CodeGroup>

## Condition Expression Syntax

The `condition` property accepts boolean expressions that are evaluated against the current application state. Supported operators:

| Operator | Description              | Example                        |
|----------|--------------------------|--------------------------------|
| `==`     | Equality                 | `user.role == 'admin'`         |
| `!=`     | Inequality               | `user.name != null`            |
| `>`      | Greater than             | `cart.total > 100`             |
| `<`      | Less than                | `items.length < 5`             |
| `>=`     | Greater than or equal    | `user.age >= 18`               |
| `<=`     | Less than or equal       | `score <= 50`                  |
| `&&`     | Logical AND              | `isLoggedIn == true && isVerified == true` |
| `\|\|`   | Logical OR               | `role == 'admin' \|\| role == 'moderator'` |

<Note>
The `condition` is evaluated at runtime by Stac's expression resolver against the current application state. State values are referenced by their key names directly in the expression.
</Note>

## Examples

### Example 1: Role-Based Access Control

Show different UI based on the user's role:

<CodeGroup>
```dart Dart
StacConditional(
  condition: "user.role == 'admin'",
  ifTrue: StacElevatedButton(
    child: StacText(data: 'Admin Panel'),
    onPressed: StacNavigateAction(routeName: '/admin'),
  ),
  ifFalse: StacText(data: 'Access Restricted'),
)
```

```json JSON
{
  "type": "conditional",
  "condition": "user.role == 'admin'",
  "ifTrue": {
    "type": "elevatedButton",
    "child": { "type": "text", "data": "Admin Panel" },
    "onPressed": {
      "actionType": "navigate",
      "routeName": "/admin"
    }
  },
  "ifFalse": {
    "type": "text",
    "data": "Access Restricted"
  }
}
```
</CodeGroup>

### Example 2: Empty State Handling

Render a list or an empty state based on item count:

<CodeGroup>
```dart Dart
StacConditional(
  condition: 'items.length > 0',
  ifTrue: StacListView(
    children: [
      StacText(data: 'Your items:'),
    ],
  ),
  ifFalse: StacCenter(
    child: StacColumn(
      mainAxisAlignment: StacMainAxisAlignment.center,
      children: [
        StacIcon(icon: 'inbox', size: 64.0),
        StacSizedBox(height: 16.0),
        StacText(data: 'No items found'),
        StacSizedBox(height: 8.0),
        StacElevatedButton(
          child: StacText(data: 'Add Item'),
          onPressed: StacNavigateAction(routeName: '/add-item'),
        ),
      ],
    ),
  ),
)
```

```json JSON
{
  "type": "conditional",
  "condition": "items.length > 0",
  "ifTrue": {
    "type": "listView",
    "children": [
      { "type": "text", "data": "Your items:" }
    ]
  },
  "ifFalse": {
    "type": "center",
    "child": {
      "type": "column",
      "mainAxisAlignment": "center",
      "children": [
        { "type": "icon", "icon": "inbox", "size": 64.0 },
        { "type": "sizedBox", "height": 16.0 },
        { "type": "text", "data": "No items found" },
        { "type": "sizedBox", "height": 8.0 },
        {
          "type": "elevatedButton",
          "child": { "type": "text", "data": "Add Item" },
          "onPressed": {
            "actionType": "navigate",
            "routeName": "/add-item"
          }
        }
      ]
    }
  }
}
```
</CodeGroup>

## Conditional vs Visibility

Both `conditional` and `visibility` can hide/show content, but they serve different purposes:

| Feature             | `conditional`                              | `visibility`                              |
|---------------------|--------------------------------------------|-------------------------------------------|
| Condition type      | Evaluated string expression                | Static boolean property                   |
| State awareness     | Yes — reads from application state         | No — uses a fixed `visible` value         |
| False branch        | Custom `ifFalse` widget                    | `replacement` widget (defaults to empty)  |
| Maintain state/size | No                                         | Yes — supports `maintainState`, `maintainSize`, etc. |

Use `conditional` when the rendering decision depends on runtime state. Use `visibility` when you need to preserve widget state or size while toggling visibility.

## Best Practices

1. **Keep conditions simple** — complex logic is harder to debug server-side. Prefer single comparisons or at most one `&&`/`||` combination.
2. **Always provide `ifFalse` for user-facing conditionals** — omitting it renders an invisible `SizedBox`, which can confuse users if they expect some feedback.
3. **Initialize state before using it** — use the [`setValue`](/widgets/set_value) widget to ensure state keys exist before the `conditional` tries to evaluate them.
4. **Use descriptive state keys** — prefer `user.isLoggedIn` over `flag1` for maintainable server-driven UIs.
5. **Avoid deep nesting** — multiple nested `conditional` widgets can be hard to read. Consider restructuring your data model instead.
